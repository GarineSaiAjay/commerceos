# CommerceOS — Rigorous Gap & Defect Audit

**Date:** 2026-08-29
**Scope:** Full repo, both `backend` (Go) and `frontend` (Next.js), plus `db/`, `infra/`, `.github/`, and every `.md` doc in `files/` and the repo root.
**Method:** Static, line-by-line review of every tracked file (`git ls-files`, 196 files) — route wiring in `main.go` cross-checked against every handler; every doc's factual claims cross-checked against the code it describes; `npm run lint` and an attempted `npm run build` run; `go build`/`go test` could **not** be run (no Go toolchain in this session's shell — see Environment limitation below), so backend findings here are from reading, not execution.
**Context:** this repo is the entry for Razorpay's "AI Growth & Agentic Commerce" buildathon track. The track's own framing — agent-to-agent commerce via protocols like ACP/AP2/x402 — is the lens several of the "Critical" findings below are judged against, because that's specifically what a technical judge will poke at.

This is not a rewrite of `files/BUGS.md` (a prior pass that fixed six reproduced usage bugs) or the project-memory audit from earlier today (security/build verification, now resolved). This is a fresh, broader sweep for anything still broken, unwired, stubbed, or inconsistent — including things that were never wrong at the code level but are wrong at the *documentation* or *claims* level, which matters just as much when ~20,000 applicants are being judged partly on their write-up.

## 1. Critical — the track's actual ask is weaker than the pitch claims

The buildathon track is about **agent-to-agent commerce**: making the merchant transactable by an external AI buyer, via something protocol-shaped (ACP/AP2/x402 are named explicitly). This repo's answer to that is the MCP server (`backend/mcp/`). `files/pitch-one-pager.md` states outright: *"An MCP server exposes the same commerce tools to any MCP-compatible client (Claude Desktop, the MCP Inspector) — this isn't a bespoke API only the demo frontend can talk to."* Three findings below say that claim is currently not true in the way a judge would test it.

### 1.1 An external MCP agent cannot actually complete a purchase — there is no add-to-cart tool

`backend/mcp/tools.go` registers exactly these tools: `search_products`, `get_product`, `create_cart`, `recommend_bundle`, `calculate_total`, `request_authorization`, `create_checkout`, `execute_authorized_checkout`, `get_payment_status`, `explain_decision`.

`create_cart` only creates an **empty** cart (`deps.Cart.CreateCart`). `create_checkout` takes a `cart_id` and calls `deps.Order.Checkout`, i.e. it checks out *whatever is already in the cart*. There is no tool anywhere in this list that adds an item/product/quantity to a cart. The only code path that can put an item into a cart is `cart.Handler.AddItem`, wired to `POST /carts/{id}/items` on the bespoke commerce HTTP API — not exposed through MCP at all.

Concretely: a strict external MCP client (Claude Desktop, the MCP Inspector, any ACP-style agent) can call `search_products`, `get_product`, and `create_cart`, but then has no MCP tool that lets it add the product it found into the cart it created. `create_checkout` against that still-empty cart will hit the checkout saga's empty-cart validation (`backend/commerce/order/saga.go`) and fail. **An agent using only the standardized MCP surface cannot complete an end-to-end purchase.** This directly contradicts the pitch's framing of MCP as a real, complete external protocol surface, and it's the single most track-relevant gap in the repo, since "agent buys through a standard protocol" is close to the literal track description.

### 1.2 Every MCP tool's input schema is an empty stub — no external agent can discover parameters

Every one of the 10 tool registrations in `backend/mcp/tools.go` sets:

```go
InputSchema: map[string]any{"type": "object"},
```

— with no `properties`, no `required`, for any tool. MCP's whole value proposition (and what ACP/AP2-style protocols lean on) is that a generic client can introspect `tools/list` and learn what arguments a tool takes without being told out-of-band. Right now, `tools/list` tells a caller nothing about, e.g., what fields `request_authorization` needs (`action`, `amount`, `currency`, `merchant`, `items`, `mandate_id`, `cart_id`) or that `create_cart` requires `cart_id`. A generic MCP-compatible agent has no schema-driven way to know this; only a caller who has already read this repo's Go source could use these tools correctly. This is a real, mechanical gap (not a judgment call) and it's a small, concrete fix: add real JSON Schema `properties`/`required` per tool.

### 1.3 `search_products`'s own description misdescribes its behavior

The tool is registered with `Description: "Search the catalog by budget and priority. Deterministic; never bypasses budget/availability."` Its handler:

```go
Handler: func(ctx context.Context, p json.RawMessage) (any, error) {
    return listProducts(ctx, deps)
},
```

`listProducts` calls `deps.Catalog.ListProducts(ctx)` — full stop, no arguments read, no filtering by budget or priority at all. Whatever JSON an agent sends as input is silently ignored, and the tool always returns the entire unfiltered catalog. This isn't a design trade-off, it's the tool's own docstring being factually wrong about what the tool does — worth fixing before a judge tries `search_products({"budget": 2000})` expecting it to filter.

### 1.4 Minor: the code's own comment miscounts its tools

`RegisterTools`'s doc-comment says *"wires the 9 narrow tools"* — there are 10 registrations (listed above). Trivial, but it's the kind of thing that suggests this file hasn't been re-read end-to-end since a tool was added.

## 3. Unwired or stub functionality (real code, but doesn't do what it appears to)

### 3.1 The Redis Stream consumer never does anything except log

`backend/events/stream_consumer.go`'s `Run`/`consumeBatch` reads every event off `commerce.events` via a real consumer group, and then:

```go
// Placeholder consumer: log the event. Analytics,
// Notification, and Audit consumers arrive in later phases.
log.Printf("[consumer:placeholder] event=%v payload=%v", eventType, payload)
```

...and acks it. This is honestly labeled in the code as a placeholder, but it means the event-driven half of the architecture (outbox → Redis Streams → consumer) only proves the pipe is connected — nothing downstream (dashboard refresh, notification, a second audit path) is actually implemented. If a judge asks "what does the event bus actually drive," the honest answer today is "nothing yet, it logs." Either wire a real consumer (even something small — e.g. push a dashboard-refresh signal) or be ready to explain this is deliberately out of scope.

### 3.2 The Growth/Analytics "Merchant Simulator" is stuck on a stale 4-product catalog

`backend/growth/simulator.go`'s `MerchantSimulator.Generate()` hardcodes:

```go
products := []string{"airpods-pro-2", "airpods-case", "applecare", "usb-c-adapter"}
```

and a matching `ProductPrices` map with only those 4 SKUs. The real catalog (`db/seeds/001_catalog.sql`) has **10** products (`airpods-3`, `airpods-eartips`, `airpods-max`, `lightning-usbc-cable`, `magsafe-charger`, `wireless-charging-pad` are the 6 missing from the simulator). This means the "Phase 6" synthetic experiment engine behind `/dashboard/experiment` and `analytics.ExperimentService` has been silently out of sync with the catalog since the catalog was expanded from 5 to 10 products (`d30f155`) — it's simulating demand for 40% of the catalog and pretending the other 60% doesn't exist. Not a crash, just a quiet accuracy gap in a feature whose entire point is to look like realistic demand modeling. Easy fix: generate `ProductPrices` from the real catalog at call time instead of a literal map.

*(To be fair: this whole feature is transparently labeled `"source": "simulated"` end-to-end, including in the UI, which explicitly says "never confused with live data" — so this is a data-freshness bug inside an already-honest simulation, not a claim of realism the code doesn't back up.)*

### 3.3 No automated migration/seed step anywhere — `docker compose up` alone leaves an empty database

`infra/docker-compose.yml` defines `postgres`, `redis`, and `backend` — nothing runs `goose ... up` or applies either seed file. `README.md`'s own "Getting started" correctly documents 3 manual follow-up commands (goose, then two `psql -f` calls, in that order) after `docker compose up`, and `files/BUGS.md` bug #5 already records a real login failure caused by getting this seed order/completeness wrong once. There is no `Makefile`, `setup.sh`, `docker-compose` init container, or any other automation wrapping these three commands into one — every fresh clone repeats the same manual, error-prone dance the project already knows produces bugs.

### 3.4 No health-gating or connection retry between `backend` and `postgres`/`redis` in Docker Compose

`infra/docker-compose.yml`'s `backend` service declares `depends_on: [postgres, redis]` with no `condition: service_healthy` (both `postgres` and `redis` *do* define healthchecks, they're just not referenced by `depends_on`). `backend/infra/db/postgres.go`'s `NewPostgresPool` calls `pool.Ping(ctx)` once and returns an error if it fails; `backend/cmd/server/main.go` responds to that error with `os.Exit(1)` — no retry loop, no backoff. On a genuinely fresh `docker compose up -d --build`, Postgres routinely isn't ready to accept connections in the first second or two after its container starts; `restart: unless-stopped` will eventually recover the backend container, but the first-run experience is an avoidable crash-loop, which is exactly the kind of thing that looks broken to a judge doing a cold start five minutes before your slot. Fix: either add `condition: service_healthy` to `depends_on`, or add a short retry/backoff loop around the initial `Ping`.

### 3.5 There is no frontend Dockerfile — the frontend is never containerized

`infra/docker-compose.yml` has no frontend service, and there's no `frontend/Dockerfile`. `README.md` step 2's bullet list ("Postgres `:5433`, Redis `:6379`, backend `:8080–8083`, frontend `:3000`") reads as if `docker compose up` starts all of that, but the frontend is only ever started by the separate manual `npm install && npm run dev` in step 4. Minor wording fix, but worth tightening so "bring up the stack" doesn't imply more than it does.

## 4. Test coverage gaps

Every backend Go package has at least one `_test.go` file **except two**:

- **`backend/auth`** — zero tests for the entire operator authentication module: `Service.Login` (credential check, session issuance), `Service.Logout`, `Service.ValidateToken`, and — most importantly — the `RequireOperator`/`OptionalOperator` HTTP middleware that gates the merchant dashboard, all `/safety/*` routes, `/audit/verify`, and the approval/run list endpoints. This is the newest security-relevant module in the repo (added specifically to close a "no authentication anywhere" gap per `files/AUTH.md`) and it's the one package with no automated regression protection. Given how central "every money action explainable, bounded and gated" is to this track's judging bar, an auth module with zero tests is the most important coverage gap to close.
- `backend/infra/db` — zero tests, but it's a 27-line pool-construction wrapper; low-priority.

CI (`.github/workflows/ci.yml`) applies `db/seeds/001_catalog.sql` before `go test ./...` but **never applies `db/seeds/002_operator.sql`**. If any test (present or future) relies on the seeded demo operator row existing rather than inserting its own fixture, it will pass locally (if you've seeded your dev DB) and fail in CI, or vice versa. Worth an explicit check that no test depends on that seed, or adding the second seed step to CI for parity with the documented local setup.

## 5. Consolidated security/robustness notes (mostly already disclosed — restated here so they're in one place)

`files/AUTH.md` is unusually candid about its own trade-offs, so most of these are *known*, not hidden — but "everything rigorously documented in one file" should still list them:

- Bearer token lives in `localStorage` (`frontend/lib/auth.ts`), not an httpOnly cookie — standard XSS exposure trade-off for a bearer-token design, already called out in `AUTH.md`.
- No login rate-limiting or lockout on `POST /auth/login` (`backend/auth/handler.go`) — a brute-force attempt against the single seeded operator account has no throttle. Already flagged in `AUTH.md` as a known simplification.
- No operator registration, invite, or password-reset flow — the only way to create a second merchant operator is a hand-written SQL insert matching `db/seeds/002_operator.sql`'s shape (including generating your own PBKDF2 hash). Fine for a single-merchant demo; worth stating explicitly if a judge asks "how would a second merchant sign up."
- `corsMiddleware` in `main.go` hardcodes `Access-Control-Allow-Origin: http://localhost:3000` with no environment override. If you deploy the frontend anywhere other than `localhost:3000` for judging (a public demo URL, a different port), every cross-origin request silently fails with no server-side error — just a browser CORS rejection in devtools. Worth making this an env var now, before you need a public URL under time pressure.
- Several audit-chain writes are fire-and-forget: `backend/commerce/payment/webhook_applier.go` (`_ = a.audit.Write(...)` on both the captured and failed paths) and `backend/commerce/order/postgres_repository.go`'s campaign-discount audit events discard the write error entirely — no retry, no log, no alert. The project's central pitch claim is that the audit ledger is complete and tamper-evident; a *dropped* row from a transient DB error during a webhook is a different failure mode than a *tampered* row, and today it would happen silently. Given how much of the pitch rests on the audit trail, this is worth at least logging loudly (even if fixing it with retries is out of scope for the timeline).
- Widespread pattern in `backend/policy/postgres_repository.go`: `json.Unmarshal` errors on the `items` JSON column are discarded (`_ = json.Unmarshal(items, &a.Items)`) in roughly 10 places. Low risk in practice (the same code writes and reads this column), but a corrupted row would silently produce an empty items list rather than a visible error, in a table that specifically exists to be inspected during an audit.

## 6. Root-level vision docs describe capabilities that were never built

`CommerceOS — Autonomous Revenue & Checkout Agent.md` and `CommerceOS — Full Build Guide (From Zero to Demo-Ready).md` (1,059 and 769 lines, both at the repo root, both prominent enough that a judge browsing the repo will open them first) describe a **"Merchant Agent"** that runs a full autonomous loop: *"analyze → identify opportunity → create campaign → select audience → choose offer → run experiment → measure → adapt"* — explicitly including **audience selection/segmentation**.

What was actually built (`backend/campaign/`, confirmed solid in the prior audit pass) is narrower and, notably, *more responsible*: it proposes a bounded discount on whichever single product has the most observed rejected cross-sell demand, sized to that volume, and requires human operator approval before anything applies. There is no audience-selection or segmentation step feeding real campaign targeting — the only segmentation-shaped code in the repo is `growth.Describe()` in the (synthetic) `MerchantSimulator`, which produces a canned "budget-conscious buyers" string from simulated data, never wired into campaign targeting at all.

This isn't a code defect — the built version is arguably the better, more defensible design for this track's bar ("bounded and gated," not "fully autonomous"). But two root-level docs still describe the more ambitious, unbuilt version, and they're the first files most readers will open. Either add a short "as-built vs. as-designed" note at the top of both, or trim the "Merchant Agent" section to match what actually shipped, so nobody reads the vision doc, then the demo, and concludes something was cut without explanation.

## 7. Smaller code-quality observations

- `backend/Dockerfile`'s final runtime stage is `FROM golang:1.26` (the full SDK image, ~800MB+) instead of a slim runtime base (`debian:bookworm-slim`, `gcr.io/distroless/base`, etc.) copying in just the compiled binary. Not a functional bug, but an easy, standard optimization for a project positioning itself as "top-notch."
- `frontend/app/dashboard/runs/page.tsx`'s `loadRuns()` calls `.then((r) => r.json())` on the `authFetch` response without checking `r.ok` first (contrast with `selectRun`, a few lines down in the same file, which does check `res.ok`). A non-200 response (e.g. an expired token mid-session) will throw inside `.json()` on a non-JSON error body rather than surfacing a clean "session expired" message — it still lands in the generic catch, so it fails safe, just with a less specific message than the pattern used two functions later in the same file.

## 8. What's genuinely solid (so this document isn't read as all-negative)

Carried forward from today's earlier verification pass, still true: the Policy Engine (`backend/policy/engine.go`) is real deterministic gating with per-check explanations; the audit hash chain (`backend/audit/`) has a real verifier; the Razorpay call counter proves blocked actions never reach the provider; the 14-attack red-team suite (`backend/safety/attacks.go`, spot-checked in this pass — all 14 are real, specific, and well-constructed, including one planted inside catalog *data* rather than a chat prompt) plus the 100-scenario evaluation suite both exist and are wired into CI; the webhook signature verifier (`backend/commerce/payment/webhook_signature.go`) correctly uses `hmac.Equal` (constant-time); the operator-auth design in `files/AUTH.md` is candid and well-reasoned about its own trade-offs; and the Campaign Orchestrator is a real, data-driven, approval-gated feature, not a stub.
